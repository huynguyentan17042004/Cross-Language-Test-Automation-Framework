# Dragon Warriors OOP Test Suite

This project is a testing suite for the **Dragon Warriors** Programming
Fundamentals assignment. It verifies the object-oriented design, individual
class behavior, full-program logic, and memory management.

> The current suite provides **requirement and functional coverage**: each test
> group covers a set of assignment requirements. It does not currently measure
> line or branch coverage percentages with tools such as `gcov` or `llvm-cov`.

## 2. Test coverage strategy

The suite is organized into four layers. Each layer detects a different type of
problem.

### 2.1. Compile-time OOP structure tests

The `test.py` script checks:

- Whether required classes and members exist with the correct names.
- Whether attributes use the required `private`, `protected`, or `public`
  access modifier.
- Whether methods can be called from outside their classes.
- Whether constructors and parameter lists are compatible with the
  specification.
- Whether selected inheritance relationships support upcasting.

Each requirement is described by a Python tuple:

```python
("Position", "r_", "attribute", "private", "d->r_;")
("Position", "getRow()", "method", "public", "d->getRow();")
```

For every tuple, the script generates an independent `probe.cpp`, for example:

```cpp
#include "dragon.h"

int main() {
    Position* d = new Position(0, 0);
    d->r_;
    return 0;
}
```

The script compiles the probe with `g++` and interprets the result:

| Compilation result | Interpretation |
|---|---|
| Compilation succeeds | The member is `public` |
| Compiler reports `private` | The member is `private` |
| Compiler reports `protected` | The member is `protected` |
| Another error occurs | The result is `unknown`, so the test fails |

Each member is compiled separately so that one compiler error does not hide
errors in other members. Results are printed to the terminal and written to
`probe_log.txt`.

Run the OOP structure tests:

```bash
python3 test.py
```

Read the generated report:

```bash
less probe_log.txt
```

The probes also use upcasting to verify selected inheritance relationships:

```cpp
Warrior* warrior = new GroundTeam(...);
MovingObject* object = new DragonLord(...);
```

These statements fail to compile if the derived class does not inherit from the
required base class through public inheritance.

### 2.2. Unit tests for individual features

The unit tests are defined in `main.cpp` and grouped by class:

| Test group | Main coverage |
|---|---|
| `TestPosition` | Constructors, row/column values, getters, setters, `str`, and position comparison |
| `TestMapElement` | Element type, required damage, and string representation |
| `TestMap` | Map creation, obstacles, ground obstacles, and position validation |
| `TestFlyTeam` | Movement, moving-rule index, collisions, attacks, and team state |
| `TestGroundTeam` | Movement, obstacles, traps, trap duration, and team state |
| `TestWarrior` | HP, damage, bags, and common warrior behavior |
| `TestLord` | DragonLord movement, combat, and state |
| `TestMovingObject` | Common interface, abstract behavior, and polymorphism |
| `TestConfiguration` | File parsing, getters, setters, obstacle arrays, and `str` |
| `TestItem` | DragonScale, HealingHerb, TrapEnhancer, and bag behavior |
| `TestSmartDragon` | Creation, target selection, and movement for each DragonType |

Each test generally follows the Arrange–Act–Assert pattern:

1. **Arrange:** create the map, characters, and input data.
2. **Act:** call the method being tested, such as `move()`, `attack()`, `trap()`,
   or `use()`.
3. **Assert:** compare the actual output or state with the expected result.

Console output is temporarily redirected to an `ostringstream`:

```cpp
ostringstream output;
streambuf* oldBuffer = cout.rdbuf();
cout.rdbuf(output.rdbuf());

// Call the behavior under test

cout.rdbuf(oldBuffer);
print_result(expected, output.str());
```

`print_result()` compares the strings exactly. Different content, whitespace,
or line breaks can cause a failure. For a failed test, it prints both `Expect`
and `Output` to make debugging easier.

### 2.3. Integration tests for program logic

Sample test cases 19–22 create a complete `DragonWarriorsProgram` from a
configuration file and call:

```cpp
program->run(true);
```

These tests cover the end-to-end workflow:

- Parsing a configuration file.
- Creating the map and moving objects.
- Moving according to each movement rule.
- Handling obstacles and opposite-direction fallback.
- Detecting encounters between teams.
- Allowing FlyTeam to attack DragonLord.
- Allowing GroundTeam to trap DragonLord and counting trap turns.
- Eliminating warriors according to the stuck-state rules.
- Creating and moving SmartDragon objects.
- Using items stored in bags.
- Determining victory or defeat.

These are integration tests because their results depend on cooperation between
multiple classes rather than one isolated method.

### 2.4. Memory-safety tests

AddressSanitizer can detect:

- Heap and stack buffer overflows.
- Use-after-free errors.
- Double-free errors.
- Invalid memory access.
- Some memory leaks.

Build and run with AddressSanitizer:

```bash
g++ -g -O0 -fsanitize=address -fno-omit-frame-pointer \
    -std=c++11 main.cpp dragon.cpp -I . -o main_asan
./main_asan
```

Leak detection can also be requested, depending on the compiler and runtime:

```bash
ASAN_OPTIONS=detect_leaks=1 ./main_asan
```

On macOS, the system `leaks` tool can run the program and inspect it at exit:

```bash
leaks --atExit -- ./main
```

A memory-safety run is considered successful when:

- AddressSanitizer produces no error report.
- There are no use-after-free, double-free, or buffer-overflow errors.
- The leak checker reports no remaining allocations caused by project code.
- The program still produces the correct logical result.

Memory testing should not be limited to one simple test case. Run the Map,
Configuration, Item/Bag, SmartDragon, and integration test groups so that the
destructors of all important classes are exercised.

## 3. Running the tests

### Run the currently enabled test cases

```bash
bash run.sh
```

Alternatively, build and run manually:

```bash
g++ -g -O0 -std=c++11 main.cpp dragon.cpp -I . -o main
./main
```

The current `main()` function directly enables sample test cases 19–22:

```cpp
TestDragonWar::satc_19();
TestDragonWar::satc_20();
TestDragonWar::satc_21();
TestDragonWar::satc_22();
```

### Run unit tests for selected classes

In the `main()` function of `main.cpp`, comment out the four sample test calls
and uncomment or add the required test groups:

```cpp
int main() {
    exe_test_pack(TestPosition);
    exe_test_pack(TestMapElement);
    exe_test_pack(TestMap);
    return 0;
}
```

Then rebuild and run:

```bash
bash run.sh
```

To run all unit-test groups:

```cpp
int main() {
    exe_test_pack(TestPosition);
    exe_test_pack(TestMapElement);
    exe_test_pack(TestMap);
    exe_test_pack(TestFlyTeam);
    exe_test_pack(TestGroundTeam);
    exe_test_pack(TestWarrior);
    exe_test_pack(TestLord);
    exe_test_pack(TestMovingObject);
    exe_test_pack(TestConfiguration);
    exe_test_pack(TestItem);
    exe_test_pack(TestSmartDragon);
    return 0;
}
```

Run one group at a time first. If one group crashes, this approach makes it
easier to identify the responsible class.

## 4. Recommended testing workflow

Run the tests in this order so that fundamental errors are found before complex
logic errors:

1. Run `python3 test.py` to verify the OOP structure.
2. Run `TestPosition`, `TestMapElement`, and `TestMap`.
3. Run the base-class tests: `TestMovingObject` and `TestWarrior`.
4. Run `TestFlyTeam`, `TestGroundTeam`, and `TestLord`.
5. Run `TestConfiguration`.
6. Run `TestItem` and `TestSmartDragon`.
7. Run integration test cases 19–22.
8. Rebuild with AddressSanitizer and repeat the important test groups.
9. Run `leaks --atExit -- ./main` on macOS.

Fix failures at the lowest layer first. For example, an error in
`Configuration` parsing can cause many integration tests to fail even when the
logic inside `DragonWarriorsProgram::run()` is correct.

## 5. Adding a new test case

Each runtime test should verify one behavior:

```cpp
void position_set_row()
{
    Position position(1, 2);
    position.setRow(5);

    string expected = "5";
    string actual = to_string(position.getRow());
    print_result(expected, actual);
}
```

Register the test in its corresponding group:

```cpp
vector<pair<string, function<void()>>> TestPosition = {
    {"Position - setRow", position_set_row},
};
```

Every new test should have:

- A name that clearly describes the behavior under test.
- A normal input case.
- A boundary input or special state when relevant.
- Expected output derived from the specification, not copied from the current
  implementation.
- Proper cleanup for every object allocated with `new`.
- No dependency on the execution order of other tests.

## 6. Current limitations and notes

- `run.sh` prints an AddressSanitizer message, but its current build command
  does not include `-fsanitize=address`. Use the command in the memory-safety
  section when checking memory.
- The `reset` command in `run.sh` may report `Inappropriate ioctl for device`
  in a non-interactive terminal. This is not a program or compilation error.
- `run.bat` currently references `dragons.cpp`, while the actual source file is
  `dragon.cpp`. Correct the filename in the Windows build command before
  running it.
- `test.py` infers access modifiers from compiler messages. An `unknown` result
  may mean that a member is missing, its signature is wrong, or another
  compilation error occurred. Inspect the compiler error to distinguish these
  cases.
